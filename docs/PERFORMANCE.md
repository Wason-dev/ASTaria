当前必须保留的帧率、省电、后台生命周期与画质取舍，集中记录在 [省电与渲染决策记录](./POWER_AND_RENDERING_DECISIONS.md)。Beta12 按用户决定把非首页工作区背景上限从 60 改为 30 FPS；首页推荐 60 FPS，首页/聊天保留手动 30/45/60/90/120 FPS。以下保留各版本真实预算与优化历史，不能把降帧、降质或解除省电上限计作同画质同帧率收益。

## v1.0 本地候选 · 2026-10-15 · 桌面性能批次

玻璃位移图的 `willReadFrequently` 提示原本意在避免场景 GPU 读回等待，但该画布实际只上传不透明像素、编码一次，不读取场景。正常画布路径消除了 Chromium 为新表面准备读回缓存的启动长任务。保留真实折射与所有位移像素；实际 Electron 中 128×38、340×680、1400×900、256×256（覆盖所有 R/G 通道值）上传并经 PNG 编解码后逐像素一致。既有位移公式另有与完整核逐像素比较的回归；这不等于已经证明 Windows D3D 像素或 GPU 时间不变。

## v1.0 本地候选 · 2026-10-15 · 手机共享优化机制与验证

`1.0.0-rc.1` 仍未公开发布。2026-10-15 的 v1.0 本地手机性能修复共享于 iOS/Android 手机构建。本节记录具体机制与隔离验证；浏览器及 Node 测量不能代替手机真机体验。

本节保留当日先完成的手机批次状态；之后桌面已接入 LUT Worker，手机包则保留该批次产物。后续桌面/共享源码及安装包的变化见上节与决策P20，不把不同批次的测试和包状态混在一起。

1. 黑洞 2048×1536 光线路径 LUT 的同一 RK4 积分移到独立启动 Worker，typed-array 转移回主线程并缓存一次；主线程不做约 300 万格积分，积分数据一字节不改，分辨率、采样、星图与亮度均未降低；桌面仍用原同步路径。生成期间界面可挂载并保留已选主题、相机与设置；Worker 失败显示场景错误，不伪造成功，也不改为主线程同步重算。
2. 原生数据库 Base64 编解码与既有字节校验保留在数据库 Worker；主线程只做受限 Base64 串检查，加上原生 `write temp`／读回原串精确相等／`rename`／`finally` 清理。64 MiB 上限、SHA 与数据库快速检查、保存确认、失败冻结回滚保留，数据文件与格式不变。
3. 长对话把静态历史与流式正文分离：完整快照相等的行与回执复用，markdown 缓存；来源内容或回执变化、思考变化、跨 topic 与午夜快捷日期仍更新。没有删除历史或内容，估时发回与草稿附件保留。
4. 手机本地只合并“同时进行、路径和 headers 相同”的 GET，不缓存已完成结果；写入的开始与结束都隔离，取消一个调用不误取消其他调用，POST 与 SSE 不合并，只减少同一轮的重复 Worker 往返与查询，数据新鲜度不延后。
5. `appStateChange` 立即派发本机 activity 事件；主黑洞、弦轨等动画、相机采样、可见轮询与分钟时钟同时尊重原生 inactive 与 `document.hidden`，回前台刷新恢复，窗口失焦不等于隐藏。
6. `visualViewport` 的 resize 按 RAF 合并，相同值不反复写 CSS 变量或键盘标记；首页相同尺寸不重复发布 layout 状态，最终尺寸和 safe-area 不变；同一帧合并事件会让视口标记最多延后一帧，原生键盘时序仍待真机检查。

审计后的补充修复：

- 只读事务不再把 sql.js 数据库标脏；20 轮四种只读请求产生 **0 次整库导出、0 次保存**。已有快照无实际升级时重开不重写；新建、升级与保存期间的新写入继续落盘。导出后恢复 `foreign_keys` 与 `busy_timeout`；超过 64 MiB 时拒绝未确认操作、回滚到确认快照，后续读取和小规模编辑仍可用，真实存储失败仍冻结。见决策 P19。
- 会话读取按 requestId 聚合思考和回执归属，批量读取轻量 turn 字段；40 ms 的可写性监测不再读取、解析整份 progress。200 条消息与 124 个操作的真实数据库对照中，完整 turn 读取由 124 次变成 0 次，SQL 查询由 327 次变成 204 次；分页、来源、撤回与展示结果保持一致。没有加入基于修订号的全局日程缓存。
- 半浮点转换使用索引循环，逐值调用原有 Three.js 转换；上下文汉字计数不再生成整份匹配数组。Base64 在 Worker 内查表编码，保留严格格式与容量检查。图片使用 FileReader 异步编码，历史图片允许异步解码，保留原始字节。
- HTML 解析器只在真实解析网页时动态加载；手机 bootstrap chunk 从约 93.3 kB 减至 35.4 kB，数据库 Worker 从约 549 kB 减至 494 kB。主入口仍约 1.52 MB，CSS 仍约 439 kB，尚未完成页面级拆包。
- 弦轨 `reveal=0` 时跳过不可见描边和渐变，仍推进几何、弹簧与状态；首次可见帧完整绘制。相同画布尺寸不重分配，销毁时释放背板，不改变动画时间或帧率。

### 2026-10-13 · 余时切换日历的重复计算与玻璃恢复

通过顶部菜单从余时进入日程，已经加载的月历原先仍反复生成整月事项与容量模型：相同 GET 返回新引用，loading 状态及页面激活更新继续触发计算。现在只在快照内容、事项、日期模式或时钟变化时重算，相同快照保留引用，缓存读取不再次开启 loading。保存期间的重新进入、焦点、本地数据事件与手动刷新合并到写入结束后读取，保存前的失效读取不再发布。比较完整快照，不能只比较 planner revision，因为余时完成记录会在修订号不变时更新。

玻璃的首次有效测量立即恢复当前尺寸；页面显示时不再等待 100 ms 的动画缩放防抖。后续真实尺寸动画仍暂停旧位移图并等待尺寸稳定，不每帧编码 PNG。隐藏日历保持不采样、不可接收输入；没有删减玻璃效果、降低画质、减少采样、修改动画时间或提高稳态背景预算。

### 2026-10-13 · 移动 WebView 兼容、Android 画质预算与系统栏

手机本机 API 的兼容实现优先使用可用的原生 `AbortSignal.any` 与 `AbortSignal.timeout`，只在未提供这些 API 的 WebView 上退回自建 `AbortController` 与超时定时器组合外部取消信号，`Response.json` 改用 `Response` 构造器，使低版本 Android System WebView 仍能读取设置、保存 API Key 与显示首次引导。这是兼容性修复，不是性能优化：本轮没有配套的移动端启动耗时、内存或初始化数据。独立旧 WebView API 条件生产流程在禁用这三个 API 的条件下通过 229 项检查，覆盖真实 Worker 日程读取、首次引导与 API Key 实际输入（未保存凭据），仍为 Mac Chrome 隔离模拟，不是 Huawei 真机。

Android Manifest 明确启用 `android:hardwareAccelerated="true"`。声明硬件加速不等于已测得 GPU 渲染效果或耗电变化；本轮没有 Android 真机、Huawei Mate XT 实机、GPU 时间、帧率或电池数据，设备渲染表现与功耗仍须真机测量。

高画质启动只限 Android 原生自动画质：先用高质量预算启动，稳定后自适应回到最高档；iOS、浏览器预览与桌面保留 Ultra 启动，手动最高画质保留。参数档位定义不变，但 Android 启动实际 DPR 由 Ultra 最高 2 调整为 High 最高 1.5，星图由 8192 降为 4096，着色器画质参数由 3 改为 2。这是明确的画质预算取舍：实际绘制分辨率与星图尺寸低于原 Ultra 启动，不能写成不变，也不计作无损提速、同画质优化或省电收益。High 与 Ultra 保留相同的三阶盘面交点，只有 `uQuality < 2`（Low/Safe）才跳过第三阶，因此不能写成 High 减少了盘面交点采样，也不能算同画质提速；本轮没有 Android GPU、电池或续航数据。

窄屏下黑洞、星点与空间投影统一略向右调整，标题说明与操作区分行显示，设置标签换行且不横向裁切（触控目标保持至少 44 px），设置页通知浮层不遮挡内容；Android 主页面系统栏与深浅主题联动，并正确使用 Capacitor 安全区避免重复留白。这些是布局与系统栏修正，不改变 P11–P13 的帧率上限与转场预算，也不改变桌面策略。

本轮增补验证：移动全矩阵 8 组 × 215 项加全局检查共 1,790 项通过（176 张截图）；当前全量源码测试 2,107 项通过（本节前文记录的 2,105 项与上一轮 1,766 项为历史结果，保留不改）。这些检查使用 Mac Chrome 隔离模拟与桌面浏览器，不能作为 iOS/Android 原生帧率、键盘、GPU 或功耗证据；平台验收状态见[候选说明](./RELEASE_NOTES_v1.0.0-rc.1.md)。

## BetaX：Windows 玻璃材质取舍与实测

BetaX 对 Windows 上玻璃边缘折射的处理是一次**明确的材质取舍，不是无损画质优化**：默认走 CSS 通透/磨砂路径，保留 rim、tint、通透与磨砂差别，但不做 SVG 精细边缘位移（`src/home/glassRendering.ts` 的 `supportsGlassRefraction` 在 Windows 上返回 false）。设置里可以单独选「精细折射」换回 SVG 位移，代价是可见的帧率下降（见下表）。**黑洞本身的最高画质、渲染分辨率、采样与辉光没有被降低**；Windows 与 macOS 都不因这一取舍改变黑洞画质档位的定义。

### 复现方式


### 限制

- 只有一个 GPU 与一种分辨率/DPR 的结果；不同 GPU、驱动、屏幕刷新率与电源模式可能差异很大，不作为所有设备的承诺。
- 8 秒样本只反映短时前台负载，不构成长时间功耗、温度、风扇或续航结论。
- 不把 `requestAnimationFrame` 回调频率（如 160 Hz 显示下的回调计数）当作黑洞帧率；判断标准始终是渲染帧。
- 精细折射在 Windows 上属于高开销选项，默认关闭；macOS 不受该默认影响。

## Beta11：保留省电预算的双平台动态优化

2026-10-05 开始的 Beta11 候选测量；其后源码合并 `main` 并作为预发布来源。目标是减少切页与聊天形变中的无用工作、误跳帧和长帧。工作区最高 60 FPS 的既有省电策略保持不变；首页/聊天保留手动 90/120，30/45 不升档，手动画质独立。原因与回归边界见[决策记录 P01–P08](./POWER_AND_RENDERING_DECISIONS.md)。

### 本版实际改动

- 高刷 RAF 时间戳容差从 0.25ms 调为 2ms；绝对截止时间仍按完整间隔推进，避免误跳帧，不提高平均目标 FPS、不补画过期帧。
- 相同有效帧率和画质的切页保留帧调度与自适应历史；预算确实改变（如首页 120→工作区 60）时正常重新调度。
- 相机几何快照、SVG 属性去重；同尺寸且 RGBA 逐字节相同的位移图复用 PNG。比较缓冲最多一张、上限 8 MiB；原位移公式、分辨率不变。
- CSS 玻璃不创建无用 SVG 和尺寸观察器；零半径 blur 使用 none。通透/磨砂、色调、边缘、反光、阴影参数保持原值。
- 浅色精确端点的 bloom 贡献为零时跳过三个中间 pass；指针强度精确为零时跳过无贡献计算，任何非零值都保留原效果。
- 工作台、日程、余时的既有 200ms 退出淡出结束后跳过隐藏布局，返回恢复可见内容、编辑状态与滚动；不卸载保留页。
- Mac 打包优先 APFS 克隆，降低临时文件占用。这是构建优化，不计入 App 运行性能。

### 2026-10-06 · 用户体验反馈与未采用的实验

用户在 Windows 10、RTX 4090 Laptop 上继续感到切页和展开聊天卡顿，因此上面的短时样本不能作为体验问题已解决的结论。为定位 GPU 成本，曾在场景着色器中尝试跳过画面零贡献的天空和光盘计算。Mac 上 48 组场景像素对照的最大通道差为 0，但 GPU 时间没有稳定收益；Windows 隔离构建的默认玻璃短测中，聊天展开 P95 为 37.4ms、最大帧间隔 62.5ms、GPU P95 为 30.1ms，工作台切入 P95 为 31.4ms。与先前候选的约 18.9ms 不能构成严格同负载因果对照，着色器改动已撤回。专用场景测量在 Windows 上还发生过无进展等待，该轮 GPU A/B 不作为证据。

撤回着色器分支后，Mac 隔离 App 在同一默认配置的聊天展开/收拢 P95 均为 18.2ms，切页约 18ms，保持 ultra 和既有 60 FPS 工作区预算。Windows 撤回后的聊天展开 P95 仍为 37.6ms、最大间隔 93.7ms；按 GPU 通道计时，场景通道 P95 约 20–26ms。随后检查测试机发现另有游戏和动态桌面等图形程序运行，`nvidia-smi` 读到 RTX 4090 Laptop 99% 使用率、83°C、约 930 MHz 核心频率和 47 W 功耗；因此这批 Windows 样本属于外部高负载条件，不能归因于本版着色器或用作正常空闲性能基线。游戏退出后的同机复测尚待完成，也不能把 Mac 数字外推到 Windows。后续应优先按用户所见的首次展开、连续切页和不同玻璃模式测量最终屏幕呈现与 GPU 各通道耗时；遇到窗口遮挡、远程会话变化或负载波动应重新取样。只有同时通过两端同画质对照和实际体验，才可称卡顿修复。

### 2026-10-06 · 聊天输入就绪延迟修复

发现一个与 GPU 掉帧独立的问题：聊天几何已达到原有 `0.99` 可输入阈值，但 imperative 相机消费者只在转场开始/结束发布 React 状态，inert 仍保持关闭；焦点 effect 也额外等待 `cameraTransition=false`。本轮仅在交互阶段边界补充状态发布，并移除焦点对完全停稳的等待。原 `0.99` / `0.01` 阈值、相机弹簧轨迹、画质、玻璃和省电预算不变，详见决策 P08。

Mac M4 Pro / Metal，1473×944 CSS、DPR 2、实际渲染 2946×1888 ultra，默认深色通透、60 FPS 的原生对照如下。基线是聊天修复前的 Beta11 工作树，**不是 BetaX**；原始报告摘要与哈希见 [beta11-chat-readiness-mac.json](./performance/beta11-chat-readiness-mac.json)。

| 聊天展开指标 | 修复前 | 修复后 |
| --- | ---: | ---: |
| 几何达到可输入阈值 | 1905.0ms | 1905.1ms |
| inert 解除 | 3020.3ms | 1905.1ms |
| 输入框获得焦点 | 3029.9ms | 1913.4ms |
| 相机完全停稳 | 3020.3ms | 3021.8ms |
